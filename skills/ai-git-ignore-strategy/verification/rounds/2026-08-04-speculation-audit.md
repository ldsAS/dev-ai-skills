# 推測性規則稽核 — 2026-08-04

**執行者**：Claude Code（維護者側自查）
**動機**：維護者提問——「還有沒有只是理論推測、也不是有官方文件依據，就用推測自己幫別的工具補檔案的部分？」

前幾輪的交叉檢視是**橫向**的（問各工具「你的機制是不是這樣」）。
本輪是**縱向**的：把範本裡每一條規則倒過來問「這條的依據到底是什麼？」

---

## 方法

三道篩，前兩道會互相補漏：

1. **帳本依據欄掃描** —— 撈出「依據」含推論性詞彙（推論／推導／對稱／類比）且不含實查詞彙者
2. **範本 ↔ 帳本精確比對** —— 每條規則正規化後找**路徑完全相同**的主張。
   ⚠️ 第一次用前綴比對，結果 0 條 —— 那是**假陰性**：`.agents/` 開頭的規則全被
   C-77（官方文件）吸走了。前綴比對會讓弱主張躲在強主張後面，必須用精確比對。
3. **實地取樣** —— 本機五個真實專案的 `.agents/`／`.agent/` 實際內容，
   加上 agy 1.0.13 二進位的路徑模板全列舉

---

## 篩出的三條

### ① C-54 `!.agents/agents/` —— 依據被**低估**了，非推測

帳本原記「二進位字串分析（架構對稱）」，並自陳「殘留未知：實體檔案內容尚無人目視」。
但重查二進位得到的是**明確路徑模板**，不是對稱推論：

```text
{workspace}/.agents/agents/{agent_name}/agent.json
{appDataDir}/agents/{agent_name}/agent.json      ← 全域對應
```

→ 依據升級為「明確路徑模板」。SKILL.md 的說明其實早就寫對了，是**帳本落後於文件** ——
帳本應為最強證據來源，反而比說明弱，這本身是個要修的問題。

「實體檔案尚無人目視」維持：五個實際專案的 `.agents/` 都沒有 `agents/`，
代表工具支援但使用者沒用過，不代表路徑不存在。

### ② `.agent/skills/` —— 規則比依據寬（真的缺依據）

範本有 `!.agent/skills/` 與 `.agent/skills/*`，帳本**查無對應主張**。追查後：

| 問題 | 事實 |
| :--- | :--- |
| 官方有講 `.agent/` 向後相容嗎？ | 有，但**只講 `.agent/rules`**（C-57），未提 skills |
| 現行二進位有 `.agent/` 嗎？ | **0 命中** |
| 那這條規則哪來的？ | 實地：`PM-tools-Dashboard-docker` 有 `.agent/skills/ui-ux-pro-max/` |
| 誰寫的？ | **第三方安裝器**（`uipro init --ai antigravity`），非 Antigravity 自身 |

→ 規則保留，但正當性要說對：是「**使用者刻意放的技能應提交**」，
**不是**「工具會讀這個路徑」。後者無依據。已登記 **C-81** 並在範本加註。

### ③ `!.agents/AGENTS.md`、`!.agents/settings.json` —— 為不存在的檔案留規則 ❌

這兩條正是維護者問的那一類。C-41／C-42 早已判定**不存在**，卻以「防禦性白名單」保留。
本輪再加兩項獨立反證：

- agy 1.0.13 二進位中 `{workspace}/.agents/` 的路徑模板**完整清單只有三條** ——
  `skills`、`agents`、`ORIGINAL_REQUEST.md`，兩者皆不在內
- 本機五個實際專案的 `.agents/`，兩者皆 **0 次出現**

→ **已自五版移除**，原處留註解說明為何移除。處置方式比照 `.codex/rollout.jsonl`：
為不存在的路徑留規則不會壞事，但會讓讀者誤以為該路徑有效，日後還可能被當成事實引用。

## 三條假陽性（是帳本索引問題，不是推測）

精確比對會把這些標成「無主張」，逐一追查後確認依據充分：

| 規則 | 實際依據 | 為何沒被比中 |
| :--- | :--- | :--- |
| `!.claude/skills/verify/` | C-53，有官方引述 | 帳本路徑欄寫到檔名 `verify/SKILL.md` |
| `!.gemini/skills/` | C-22 主張內文 | 路徑欄只列了別名 `.agents/skills/` |
| `.agents/**/ORIGINAL_REQUEST.md` | 系統提示原文：「append it to `.agents/<your_folder>/ORIGINAL_REQUEST.md`」 | `**` 萬用字元 |

> 📌 這說明**帳本路徑欄要填具體路徑**（README 已載明）—— 否則自動比對照不到，
> 稽核時得靠人工追，而人工追很容易漏。

## 一個方法論結論

規則出錯的方向不對稱，稽核時該按這個優先級看：

| 規則類型 | 推測錯了會怎樣 | 稽核優先度 |
| :--- | :--- | :--- |
| **白名單**（`!path`） | 把執行期狀態／敏感內容**提交上去** | 🔴 高 |
| **排除**（`path`） | 少提交一個本來可以提交的檔 | 🟡 低 |

本輪三條裡，①③ 都是白名單 —— 剛好落在高風險側，不是巧合：
**白名單是「我認為這個檔該分享」的主張，比排除更需要證據。**
