## 二、訊號一：`.claude/` 消失 → 語彙搬遷

官方 skills 頁現在每一處 `.claude` 都帶更長後綴，沒有一處寫裸目錄：

```
29  .claude/skills/          7  .claude/commands/        4  .claude/skills/synced/
 3  .claude/agents/          1  .claude/settings.json    1  .claude/settings.local.json
```

**關鍵事實**：`.claude/` 仍存在於另外三個 claude-code 來源的 baseline ——
`claude-code/changelog`（`.claude`、`.claude/`）、`claude-code/memory`（`.claude/`）、
`claude-code/settings`（`.claude`）。它離開的是 skills 頁，不是官方文件。

**為什麼會炸成 10 條主張**：`.claude/` 是單段目錄 token，`claims_for_token()` 的雙向前綴
比對會命中它底下全部主張。`_claim_paths()` 早就把單段目錄逐出**帳本側**比對範圍
（README〈比對規則〉：「否則該目錄底下任何異動都會被算成同一條主張，失去指向性」），
**token 側卻沒有對稱規則** → 新增 **C-99**。

## 三、訊號二：`/.claude/skills/` 新增 → `<subdir>/` 佔位符殘留

逐字出處只有一處，即 skills 頁 `where-skills-live` 表格的 **Nested** 列：

```
| Nested | `<subdir>/.claude/skills/<skill-name>/SKILL.md` | Sessions started in or
  below `<subdir>`. …
```

來源是 `.md` 原文，`normalize()` 的 HTML 剝除**未觸發**（`body[:2000]` 無 `<!doctype html`／`<html `），
`<subdir>` 因此逐字留存；`TOKEN_RE` 的前綴組 `(?:(?:~|$HOME|\.{1,2})?[/\])?` 吃下它後面的 `/`，
token 就多了一個前導斜線 —— 而 `_norm_path()` 只做 `rstrip("/")` → 對不到任何主張，
被誤丟進「🆕 帳本查無對應主張」區 → 新增 **C-98**。

**正確歸屬：C-06 `.claude/skills/` 的 nested 位置。**

**機制本身也不是新的** —— CHANGELOG **2.1.178**：

> Skills in nested `.claude/skills` directories now load when working on files there;
> on a name clash, the nested skill appears as `<dir>:<name>` so both stay available

本次真正變動的是「文件把這個既有機制寫進 where-skills-live 表格」。
同族的 nested 行為另見 2.1.211（nested `.claude/rules/*.md`）與 2.1.260（nested skill 的 deny 規則）。

> 📌 值得記下的一點：**這個機制上線時（2.1.178）監控完全沒響**，因為當時文件沒有
> 對應的路徑 token。token 監控偵測的是「文件怎麼寫」，不是「工具怎麼做」——
> README 的 (a)(b)(c) 三分法早就講過這件事，本輪是它第一次以具體例子現形。

## 四、分類副產物：monorepo 子目錄的 `.claude/` 不在範本射程內（C-97）

gitignore 語意：**含中段 `/` 的 pattern 錨定在 `.gitignore` 所在層級**。
因此根目錄那組 `.claude/*` 系列規則碰不到 `apps/web/.claude/`。實測：

| 路徑 | 修正前 | 修正後 |
| :--- | :--- | :--- |
| `.claude/settings.local.json` | IGNORED | IGNORED |
| `.claude/settings.json` | TRACKABLE | TRACKABLE |
| `.claude/skills/verify/SKILL.md` | TRACKABLE | TRACKABLE |
| **`apps/web/.claude/settings.local.json`** | **TRACKABLE ❌** | **IGNORED ✅** |
| `apps/web/.claude/settings.json` | TRACKABLE | TRACKABLE |
| `apps/web/.claude/skills/deploy/SKILL.md` | TRACKABLE | TRACKABLE |
| `apps/web/.claude/commands/deploy.md` | TRACKABLE | TRACKABLE |

官方自己寫進 global git excludes 的正是不錨定的寫法：

> the first time Claude Code writes the file in a git repository that doesn't already ignore it,
> it adds `**/.claude/settings.local.json` to your global git excludes file
>
> If you created the file by hand and Claude Code hasn't written to it yet,
> add it to `.gitignore` yourself

**刻意不誇大暴露面**：Claude Code **自己不會**在子目錄建這個檔 —— 同頁明載
「If you start Claude Code in a subdirectory of a git repository, it reads and writes that file
at the repository root」。風險僅限**手動建立**的情境，而官方在該情境正是要求自行加 `.gitignore`。

### 本輪刻意不處理的殘留

nested `.claude/skills/` 在範本中**完全放行**，與根目錄「`.claude/skills/*` 擋下、需 scoped
allowlist」不對稱。維持現狀的理由：nested 專案技能依官方定位就是團隊共享（monorepo 子專案
自帶技能），且**尚無證據**顯示任何 CLI 會把第三方技能裝進子目錄。比照 C-94 的處置 ——
位置與分享定位未定者，本輪只登記、不改規則。
