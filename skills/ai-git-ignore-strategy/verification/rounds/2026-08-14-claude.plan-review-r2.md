## 二、會不會過於複雜？→ 可接受，一處可再簡化（非缺陷）

**第三節有一條把天花板釘住的自我約束，值得肯定**：

> 不加入事件匯流排、資料庫、額外套件或長期 validation mode；
> 本輪只允許一個小型、純標準函式庫的 CI policy helper。

明寫「`check-updates.yml` 呼叫 helper 取得 outputs，**不在 YAML 重寫第二份判定邏輯**」，

**所以這是取捨不是缺陷，照 Codex 的做法也合理。**

## 四、⭐ 唯一建議動工前決定的：D5 的 Antigravity minor 告警　→ ✅ 已採納

> 📌 **本節的建議已於 2026-08-14 由 Codex 採納並寫入計畫。** 以下保留提出時的分析與數據；
> 採納後的驗證見**第六節**。

**這一項直接關係到維護者「不要整天收到提醒」的需求，而合併版沒有處理。**

D5 保留 `ALERT_LEVEL = {"antigravity": "minor"}`，理由改寫為
「次版本適合作為重新實機複驗的**低頻**提醒」。但實測：

```
2026-08-04  antigravity 2.4.3 → 2.5.0
2026-08-08  antigravity 2.5.0 → 2.6.0
2026-08-12  antigravity 2.6.0 → 2.7.1
2026-08-13  antigravity 2.7.1 → 2.8.0

→ 4 次／9 天，平均每 3.0 天一次
```

**每三天一次不叫低頻。** 而且三個支撐理由逐一查證後全部不成立：

| 理由 | 查證結果 |
| :--- | :--- |
| 原始理由「Antigravity 沒有公開文件站」 | **P1-2 自己承認是錯的**。實查 `SOURCES`：Antigravity 有 **8 個**監控來源，是所有工具中最多的（claude-code 4、codex 5、copilot 5、gemini-cli 4） |
| 「帳本有數條盲區只能靠交接維持新鮮度」 | 兩個盲區是 **C-24**（`~/.gemini/tmp`，Gemini CLI）與 **C-78**（`User/workspaceStorage`，VS Code）。**沒有一條屬於 Antigravity** |
| 新理由「低頻提醒」 | 實測每 3 天一次 |

另查：`--coverage` 顯示有 **18 條主張**由 antigravity 來源涵蓋。
路徑事實已經被 token 監控看著了，版本告警現在既**重複**、又是**最吵的那一個**。

在合併版的政策下，一般 `0.x` minor 與所有 patch 都已不告警 ——
**Antigravity minor 會成為版本類告警唯一且幾乎全部的來源。**

### 建議

D5 自己留了逃生門：

> 若實際運作證明它仍過於頻繁，直接把 Antigravity 降回 major。

**資料已經證明了，不必等到上線後再觀察。** 建議本輪就降回 major。

## 附錄：我的分類器，三個 bug

同一支還原分析腳本，我連續寫錯三次，**每次都不會報錯**：

| 次序 | Bug | 後果 | 誰發現 |
| :--- | :--- | :--- | :--- |
| 1 | 把「新工具首次納入」誤分類成「版本跨 minor」 | 該類數字偏高 | 自己 |
| 2 | 遇到 token 異動就 `continue`，跳過該 commit 的版本分析 | 0.x minor 從 3 次少算成 1 次 | Codex |
| 3 | 未排除**人工 commit**，把 bootstrap 當成可消除項 | D3 可消除數從 4 多算成 5 | 自己（比對 Codex 的數字後追查） |

三次都是「漏掉一個排除條件」。**分類器出錯不會拋例外，只會給出看起來合理的數字** ——
與本技能一貫關注的失效模式完全同型。

> 這強化了上一輪的建議：實作階段 5 的測試時，**也要為判定／分類邏輯本身補 fixture**。
> 用來衡量問題的工具，跟被衡量的程式一樣需要被驗證。

另附一個實作時會遇到的小坑：Windows 上用 `subprocess` 取 `git log` 輸出，
若不指定編碼會以 CP950 解碼而拋 `UnicodeDecodeError`（commit 訊息含中文）。
需 `.decode("utf-8")` —— 與 `7635593` 修的是同一類問題。
