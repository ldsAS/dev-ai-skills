## 二、建議補的六點

### 1.　P0 的修正沒有回歸測試保護（結構性不對稱）⭐

階段 5 的離線測試涵蓋 `check_updates.py`，也就是 **P1 類**問題。
但 **P0-1／P0-2 的邏輯住在 YAML／shell 裡**，只靠階段 6 手動驗收一次。

依這個專案剛立的原則（C-89）：

> 寫完斷言後，故意把某條決定改壞，確認 CI 真的會紅。
> **沒被驗證過的斷言，跟沒有斷言一樣。**

一次性手動驗證擋不住日後回歸 —— 結果是**最高風險的修正拿到最弱的保護**。

**建議**：把「signal 解析 ＋ gate 判定」抽成獨立腳本（例如 `scripts/ci_signal_gate.sh`），
workflow 呼叫它，離線測試餵 fixture `report.md` 驅動它。這樣 P0 也進得了測試矩陣。

### 2.　驗收指令會踩到 import 問題

`python -m unittest tests/test_check_updates.py` 這個**呼叫形式本身可行**，我實測過
（自 repo root、含目錄分隔符，exit 0）。問題在別處：`scripts/` 不是套件。

```bash
python -c "import check_updates"
# → ModuleNotFoundError: No module named 'check_updates'
```

**這不是 blocker，只是計畫需指定其中一種載入方式。** 兩種都可行，我都實測過：

| 方式 | 副作用 |
| :--- | :--- |
| `sys.path.insert(0, "scripts")` | 簡單，但會污染 `sys.path` |
| `importlib.util.spec_from_file_location()` | 不動 `sys.path`（實測 `sys.path` 確實不含 `scripts`） |

**建議**：階段 5 明寫採用哪一種即可，避免實作時第八節的驗收指令跑不起來。

### 3.　D3 的效益要先校準期望值

我逐一還原每個 commit 的前後 `last_checked.json` 比對其性質。工具層級的 patch bump
雖多，但**多數搭著 token 異動一起 commit**，那些仍會寫回 baseline，D3 消除不了。

分母要講清楚（初版用 `git log -20` 的任意上限，混進 schema 1 與人工 commit，
數字不精確）。以 schema 2 為範圍重算：

| 範圍 | 數量 | D3 消除比例 |
| :--- | ---: | :--- |
| schema 2 觸及 baseline 的 commit | 19 | **3/19 ≈ 16%** |
| 其中真正的 bot baseline commit | 12 | **3/12 = 25%** |

無論用哪個分母，「**只能消除少部分、不是大多數**」的結論都成立。

**建議**：把這個數字寫進計畫。否則上線後 commit 照樣每週出現，
容易被誤讀成「修正沒生效」而回頭改壞正確的邏輯。

> 附帶一個 D3 的已知副作用（可接受，但值得寫明）：patch-only 不寫回 baseline 後，
> 基準線的版本欄會停在舊值，於是報告顯示的差異會變成「自上次**有意義**基準線以來」
> 的累積值（例如 `2.1.226 → 2.1.231`），而非日對日。
> 告警正確性不受影響（門檻比對仍取前綴），純粹是報告語意，建議在報告用語上標明。

### 4.　D4 的風險我原本擔心過頭 —— 實測後支持

我的初始假設是：**把 0.x minor 升級成告警，會讓 Codex／Gemini CLI 洗版**
（兩者 minor 跳得很勤）。這個假設**不成立**。

schema 2 範圍內的 0.x minor 轉移**共 3 次**（初版只算到 1 次，是我的分類器
在遇到 token 異動時直接 `continue`，跳過了那些 commit 的版本分析）：

| 日期 | 轉移 | D4 生效後 |
| :--- | :--- | :--- |
| 2026-08-06 | `gemini-cli 0.53.1 → 0.54.0` | 同 commit 已有 token 異動，**本來就會告警** |
| **2026-08-07** | **`codex 0.146.1 → 0.147.0`** | **純版本週期 —— 這次才是 D4 新增的獨立告警** |
| 2026-08-12 | `gemini-cli 0.54.4 → 0.55.1` | 同 commit 已有 token 異動，**本來就會告警** |

**3 次轉移中，只有 1 次會新增獨立告警週期。**
所以「不至於洗版」的結論成立，但「只有一次 0.x minor」是錯的 —— 兩者要分開講。
D4 可放心做。

> 這一項留在文件裡是刻意的：假設被自己的數據推翻，比假設成立更值得記錄。
> 而修正過程本身又暴露了第二個分類器 bug，見附錄。

### 5.　D2 recovery 的多張同標題 issue 處理未定義

**先更正我自己**：初版列了「必須在 `updates == true` 但 `failure != true` 時也執行」，
說它是遺漏 —— **那是我看漏了**。計畫第 127 行已明確寫「當 `failure != true` 時」執行
recovery，本來就涵蓋這個情境。只是可以再補一個例子（昨天失敗、今天健康但有異動）
讓實作者不會誤寫成「無異動才 recovery」。

真正未定義的只有一項：**同標題多張 open issue 時怎麼處理**。
現行 notify step 用 `.[0].number // empty` 只取第一張；recovery 應明示是
「只關第一張」還是「全關」，兩者行為不同。

### 6.　階段 6 的 validation mode 是在有寫入權的 workflow 開後門

`check-updates.yml` 持有 `contents: write` ＋ `issues: write`。
加一個「可製造假失敗」的 dispatch 入口，等於讓任何能觸發 workflow 的人
製造假 Issue 或假 baseline commit。

**建議**：validation mode 硬性不得推 baseline、且使用**不同的 issue 標題**
（避免污染真實告警串），並在驗收完成後移除該入口。

## 附錄：本複審用到的還原分析

近 N 次 baseline commit 的性質分類（可重跑）：

```python
# 對每個 commit 取 <sha>^ 與 <sha> 兩版 last_checked.json，比對：
#   sources 不同           → token 異動（真訊號）
#   僅 versions 不同 且 前兩段相同 → 純 patch
#   僅 versions 不同 且 為 0.x    → D4 將升級為告警
#   舊版沒有該工具          → 新工具首次納入
```

**這個分類器我寫錯了兩次**，兩次都是靜默的：

| 次序 | Bug | 後果 |
| :--- | :--- | :--- |
| 第一次 | 把「新工具首次納入」誤分類成「版本跨 minor」 | 該類數字偏高 |
| 第二次 | 遇到 token 異動就 `continue`，**跳過該 commit 的版本分析** | 0.x minor 從 3 次少算成 1 次 |

第二個 bug 是 Codex 指出後才發現的。**分類器本身出錯不會報錯，只會給出看起來合理的
數字** —— 與本技能一貫關注的失效模式同型。

> 建議：實作階段 5 的測試時，**也為分類／判定邏輯本身補一個 fixture**。
> 這輪的教訓是「用來衡量問題的工具，跟被衡量的程式一樣需要被驗證」。

另附一個實作時會遇到的小坑：在 Windows 以 `subprocess` 取 `git log` 輸出時，
若不指定編碼會以 CP950 解碼而拋 `UnicodeDecodeError`（commit 訊息含中文）。
需 `.decode("utf-8")`，與 `7635593` 修的是同一類問題。
