## 為什麼還一直有問題

1. **修正尚未部署，紅燈不能直接歸因新版。** 收尾唯讀 `gh run list --workflow check-updates.yml --limit 4`：10-01 `36802867809`、09-30 `36656581278`、09-29 `36509117280` 都 failure，head 都是 **3816ac7**（PR #22 合併前）；09-28 的成功 head 是 711fddc。沒有一個正式 run 用本輪修復。因此 #20 還開著不代表這批修正又失效；合併後正式恢復仍須另驗，本輪沒有正式觸發來掩蓋等待狀態。
2. **先前驗收鎖了 parser／規則，沒有完整鎖住交付契約。** 通知失敗卻吸收 baseline、舊 issue 關閉競態、外部文字偽造訊號，以及保留 SHA 但修改正文，是不同失敗路徑。只看 helper 通過、CI 綠或 SHA 相同無法證明報告確實保存。本輪用真 workflow shell、真 policy／guard、假遠端故障與反證把這些契約接起來。
3. **官方文件仍在變，文件與不同產品 surface 也會不一致。** 新 skills.md 6256 bytes，與盤查時 6134 bytes 不同；CLI 表格仍寫 antigravity-cli，但本機 1.2.14 的唯一 probe 實際從 config 讀取。這類差異應保留版本與來源證據，不能直接把 Claude 建議、其他子系統 changelog 或 Git 放行當 runtime 定論。新版本／路徑異動是監控正常提醒，只有取得、判讀或交付錯誤才是機制缺陷。
4. **帳本追加與狀態老化原本缺少結構檢查。** loader 讀得出孤立列，所以既有測試沒發現表格閱讀損壞；退役列與政策例子也混進現行對應。本輪補結構、摘要與成員集合檢查，避免用總數或「可解析」代替正確性。
5. **仍有明確未核准的擴充。** G2 CLI major、G3 裸檔名候選、G4 404 後額外探測未做；完整 M2／M3 backlog 也不因此次九項盤查全部完成。這些是已標明的缺口，沒有偷偷增加機制或宣稱零盲區。
