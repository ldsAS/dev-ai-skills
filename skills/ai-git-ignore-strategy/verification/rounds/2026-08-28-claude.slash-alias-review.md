## 三、Codex 連帶抓到的 bug：上下文會指向錯的路徑

這一項比表面重要，值得單獨寫。

原本的 `context_for()`：

```python
index = text.find(token)          # ← 子字串搜尋
```

`.claude/skills` 是 `.claude/skills/deploy/SKILL.md` 的**前綴**，
所以 `find()` 會先命中那個較長的路徑，把它的前後文當成 `.claude/skills` 的上下文回傳。
Issue #10 正是受害者 —— 它為一個「指令範例」附上了「commands 併入 skills」的說明。

### 為什麼這不只是顯示問題

D6 立的規矩是「**新增 token 一律視為候選訊號**，取得上下文後再判定是機制、使用者自訂、
文件範例還是無關字串」。

**上下文就是那一步的唯一輸入。** 上下文錯了，D6 的第一步就已經在錯的證據上做判斷 ——
這與 C-17（把文件範例中的 `/workspace/.codex/rollout.jsonl` 當成真實路徑）
是同一種失效模式：**看到的不是原文該有的那一段**。

修法是改走實際 match span：

```python
for matched, match_start, match_end in iter_token_matches(text):
    if matched != token:
        continue
    ...
```

## 八、本輪的教訓

**假陽性的正確處理方式是修判準，不是修帳本。**

這次很容易走成另一條路：把 `.claude/skills` 當成新 token 登記進 `CLAIMS.md`，
帳本會多一條「正確但無用」的主張，而製造假陽性的判準原封不動 ——
下一次換個路徑再來一遍。

Codex 選的是修判準。這與 D6「token 是線索，不是結論」是同一個方向：
**線索的品質有問題時，該修的是取得線索的方式。**

第二個教訓來自第三節：
**顯示層的 bug 可以是判斷層的 bug。** `context_for()` 看起來只是「Issue 好不好讀」，
但它供給的是 D6 分類的唯一證據。這類 bug 不會報錯，只會讓人**在錯的證據上做對的推理**。
