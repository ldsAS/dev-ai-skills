## 2. P1：來源與版本解析一起修復

### 2.1 單一正文來源

- 將 `ANTIGRAVITY_CHANGELOG` 定為 `https://antigravity.google/docs/changelog.md`，移至 `SOURCES` 建立之前。路徑來源、版本 getter、版本來源 label 及本輪版本摘要共用此常數；一併替換 `version_sources` 現行另寫的 `antigravity.google/changelog`，確保失敗診斷及 major 告警也指向新 URL。
- `SOURCES` 的 key 保持 `antigravity/changelog`。新正文仍涵蓋四個產品區段，與上次 Rules／Workflows 分頁縮小範圍的情況不同，無需新 key 或 bootstrap。
- 修正「changelog 無 .md 端點」及舊發行表格式的過時註解；來源總數依目前為 28，不新增重複 HTML 來源。
- 保留重試、HTTP 失敗、零 token 防護與上次成功 baseline。此修復使用人工確認的固定端點，不加入自動跟隨 meta-refresh 或廣泛替代 URL 探測。
- 本批維持 source 與版本 getter 各抓一次，不加入跨呼叫快取。兩者共用 URL 不代表正文屬同一快照；版本摘要只證明 getter 本輪取得的結果。單輪共用正文另列第 7 節，不能跨輪用舊正文冒充本輪成功。

### 2.2 版本欄位的明確語意

`versions.antigravity` 延續**產品應用程式版本**的用途。新文件的 `## Antigravity 2.0` 是此欄的對應區段；CLI、SDK、IDE 版本不混入此值，也不在本批增加獨立版本欄位。09-29 產品候選值為 **2.18.1（September 28, 2026）**。

新增可獨立測試的純解析函式，輸入 `fetch()` 解碼後的原始 Markdown，回傳所選發行記錄的版本、實際區段名稱、發行日期與標題行號。版本解析不先套用會改寫 HTML／跳脫文字的 token 用 `normalize()`；路徑抽取流程維持現狀。契約如下：

1. 先辨識 fenced code block，再找區段。支援至少三個 backtick 或 tilde 開啟、同類字元且長度不少於開啟符號的獨立 closing fence；允許 Markdown 常用的零至三個前導空格及開啟行的語言標記。忽略已配對 fence 內的標題／範例；若讀完全文仍未閉合，明確失敗，不讓後續區段被靜默吞掉。
2. 只在唯一的 `## Antigravity 2.0` 區段內解析，到下一個非程式碼二級標題為止。缺少或重複產品區段均失敗；診斷列出預期名稱與實際看到的所有非程式碼 H2（沒有就明示無），提示「區段可能改名，需核對是否涉及產品主版本更名」，不直接斷言已升 major，也不改抓其他產品。診斷中的文件標題以安全文字呈現，不得產生額外的 CI 訊號標記。
3. **候選辨認採寬條件（N2）**：產品區段的 H3 內容去除前後空白後符合 `^\[?v?\d+\.\d+`，或含指向 `/releases` 的 Markdown 連結，就算發行候選。此層不要求連結存在、tab 正確、版本完整或日期合格；`### v2.19.0`、`### 2.19.0`、`### [2.19.0](/download#antigravity-app)` 都須進入嚴格驗證並報錯。其他 H3 是一般功能標題，正文中的版本字串不算候選。獨立重跑第二輪第六節，現行非發行 H3 誤命中為 0。
4. **候選合格採嚴條件**：整個 H3 內容須是 `### [vX.Y.Z](...)` 所表示的版本連結（可有 Markdown link title），版號完整為三段數字；URL 路徑為 `/releases`，`tab` 唯一且等於 `hub`，`version` 唯一且與標題一致。接受目前的相對連結形式，不能靠包含某個字串就判合格。辨認得到但不合格，立即失敗，不退回當一般功能標題。
5. 發行標題之後允許空白行及可選的單個 `Latest` 標記，再接獨立的英文日期。用明確月份對照及日曆驗證日期，不依作業系統 locale；日期必須位於這筆記錄的開頭，不能跨過一般功能標題或下一筆發行候選借用其他日期。
6. 產品區段的候選全部通過後，以數值三元組選取最高版本；不取全文最大版本、不靠第一筆或 `Latest` 決定結果。沒有任何合格候選、收到轉向 HTML／非 Markdown 正文或格式不符時，拋出帶來源與原因的例外，**不得回傳 `None` 當作成功**，也不得略過損壞的新記錄後回退舊版本。

本批**不實作 prerelease 辨識／略過政策**。任何已辨認候選若不是完整 `X.Y.Z`，包括人工反例 `v2.19.0-rc.1`，一律視為未支援格式並報錯；未來官方真的出現時再依證據決定政策。不保留會猜測其他產品版本的舊格式 fallback。

**N3／N4 診斷契約**：每筆解析錯誤附 canonical 來源、原因、出錯標題原文及原始 Markdown 的一基行號；日期錯誤指向所屬發行標題，未閉合 fence 指向開啟行。不存在產品區段時列實際 H2 及行號。新增診斷與版本摘要的外部文字先把控制字元／換行壓成空白，最多保留 240 個文字字元並標示截斷，再做 HTML escape，將方括號與反引號轉成 HTML entities；因此原始報告不會包含外部輸入的 `[SIGNAL:`，也不能由換行／反引號跳出顯示範圍。測試使用三種保留訊號、HTML、換行及長標題核對 `analyze_report()` 的結果。既有摘錄／npm 舊報告區塊的通用問題不在本批重構。

產品區段內未來出現 `3.0.0` 應照常進入 major 告警；若官方連區段名稱也改成 `Antigravity 3.0`，則產生帶觀測標題的 `CHECK_FAILED`，不宣稱此情況仍能產生正常 major 告警。

### 2.3 解析失敗的既有處理路徑

讓 `fetch_antigravity_version()` 的例外進入現有 `main()` 版本抓取失敗分支，產生 `version/<來源 URL>` 診斷與 `[SIGNAL: CHECK_FAILED]`，保留舊 `versions.antigravity`。本批不全域改動 npm getter 的 `None` 語意，不改 workflow 訊號格式。

路徑與版本是獨立結果：若路徑取得有效新內容但版本解析失敗，可照既有政策保存成功來源的異動；版本仍保留舊值，workflow 仍失敗，恢復步驟仍不得執行。若來源抓取／空集合防護失敗，則該 source entry 也必須完整保留。其他成功來源照現有邏輯運作。

### 2.4 每輪版本觀測摘要（R4）

現行報告只列版本差異；預先遷移至 2.18.1 後，正式 run 若取得相同版號，報告就沒有版本證據。採用固定摘要補足，不刻意保留落後版本作一次性提示。

- 建立僅存於本輪記憶體的版本觀測結果，與會沿用 baseline 的 `new_versions` 分開。每個 getter 紀錄取得的版號／未取得／失敗及來源；成功才可稱為本輪取得，不能把保留的 baseline 版號填入成功欄。
- 每次一般監控報告均印出 `<details>`「本輪版本取得結果」，列出三個 npm 工具及 Antigravity。成功的 Antigravity 列包含版號、canonical URL、**parser 回傳的實際區段名稱與所選記錄的發行日期（N1）**，即使版本與 baseline 相同也要出現；禁止用常數補成已解析證據。getter 若只回傳版本字串，摘要只能列版號，不能出現區段或日期；npm 列標明對應套件來源。
- getter 拋例外時列「未取得（失敗）」，詳細原因沿用失敗區段；npm getter 回傳 `None` 時列「未取得（空值）」，沿用現行非告警政策。Antigravity 格式不合契約仍必須拋例外，不能以空值列掩蓋解析失敗。
- 摘要不加入持久化 schema，不參與 `has_update`、`meaningful_baseline_change` 或 issue 通知判斷，不改 CI 訊號格式。原有版本差異參考與 major 告警保留。
- 正式驗收讀取同一次 run 的規則式報告／job summary，必須能看到本輪版號與區段。現有 workflow 已將報告存至 job summary，本批無需修改 workflow 或只靠「沒有失敗」推論版號。

| 正常解析 | 四區段 fixture 只回傳產品版本；支援有／無 `Latest`、空白行、數值排序 2.9.0／2.10.0、產品 3.0.0；其他區段更大版本及正文／程式碼範例不影響結果 |
| 失敗解析 | 無連結的新版 `### v2.19.0`、`### 2.19.0` 及無 v 的連結標題放在有效舊版之前；錯誤 tab、重複必要參數、version 不一致、非 `X.Y.Z` 後綴、無效／缺少日期、HTML 轉向頁均失敗；保留有效舊記錄驗證不能靜默回退，並斷言錯誤含標題原文與原始行號 |
| 區段／fence 診斷 | 缺少／重複／改名產品區段失敗，診斷包含預期與實際 H2；程式碼內假 H2／版本不參與解析；backtick／tilde 未閉合均失敗。標題被輸出為診斷時不得額外觸發 CI 訊號 |
| 真實 getter 整合 | mock 網路正文，實際執行版本 getter 與 parser；不得用「getter 固定回傳版本或 `None`」的既有 stub 冒充版本解析驗證 |
| 每輪版本摘要 | 透過真實 parser 取得與 baseline 相同版本時仍印出版號、URL、回傳的區段與日期；以不同日期的候選證明摘要選用所選記錄，getter 只有版本字串時不得印區段或日期。minor／major 保留原訊號政策；例外不能把 baseline 舊值列成本輪取得，npm `None` 顯示空值而不新增告警 |
| 摘要無寫入副作用 | 在暫存 baseline 非 dry-run 執行無異動案例，報告有摘要但沒有 update／baseline 訊號，檔案 bytes 不變；失敗案例仍有 `CHECK_FAILED`。用既有 `monitor_ci_policy.analyze_report()` 核對摘要不改 workflow 決策 |
| 部分失敗保留 | 有效 token＋版本解析失敗時產生 `CHECK_FAILED`、保留原版本；另讓一個成功來源變動，驗證確實寫檔後的完整預期 payload，避免因根本沒寫檔而假通過 |
| 來源失敗保留 | HTTP 404／零 token 等失敗保留完整舊 entry；重試與失敗訊號不退化；全來源 dry-run 前後 baseline bytes 相同 |
| 既有政策 | minor／patch 仍只供參考，不單獨觸發更新；major 保留告警；token 比較、精確上下文、Rules 修復及其他來源維持既有行為 |
| 遷移範圍 | 對最新基底做完整 JSON 深度比對，唯一可改欄位為上節兩項，並核對已分類 token 差集 |

執行完整現有單元測試（`python -X utf8 -B -m unittest discover -s tests -v`）。做三個定向反證，逐一記錄命中的測試：① 只換 URL 卻保留舊 parser；② 解析失敗改回靜默 `None`；③ 將產品區段內的版本選擇改為全文發行標題的數值最大值。第三項須被人工高版本反例攔下，不能讓殘留的 `tab=hub` 篩選掩蓋突變。三者均須讓相應測試轉紅，還原後通過；只在隔離／暫存環境執行，不把突變留在工作檔。

完成上述測試後，對實作時最新 baseline 做一次全來源 live dry-run，記錄來源結果、產品版本、訊號與 baseline 前後指紋。將上游新增事件與本修復失敗分開判讀。五版範本未改，不重跑 installer 或把舊的範本測試數字算成本輪成果；若實作意外涉及範本，先修訂範圍並補相應 Git 邊界驗證。
