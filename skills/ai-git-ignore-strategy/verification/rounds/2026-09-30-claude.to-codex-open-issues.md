## 各項細節

### 1　告警被埋進即將關閉的 issue

**現行行為**：[`check-updates.yml`](../../../../.github/workflows/check-updates.yml) 第 166～204 行，用 `monitor_ci_policy.py targets` 找**標題完全相同**的 open issue，有就 `gh issue comment` 追加（第 199 行），沒有才新開（第 202 行）。Commit baseline 步驟（第 226 行起）在同一個 run 裡寫回，所以異動一旦被報過，下一輪就不會再報。

**已發生過**：2026-09-11，一則告警在 06:03 UTC 追加進 #12，而 #12 在 09:58 UTC 隨 PR #13 合併關閉。那則告警一度只存在於已關閉的 issue 裡，baseline 也已吸收該 token（`faa3160`）。詳見 [#12 末則留言](https://github.com/ldsAS/dev-ai-skills/issues/12)，當時列了三個可選方向，都未實作。

**近期的具體風險**：PR #22 合併後，第一次正式 run 會把兩個 `installed_plugins` token 追加到 #15。#15 裡已有 09-26、09-28 兩則已分類的訊號；如果維護者只看前面的留言就關閉 #15，新的這則就會被埋掉。

**要確認**：

- 除了「隨 PR 合併關閉」，還有哪些情況會觸發（例如手動關閉、`Closes #15` 寫在其他 PR）；
- M3 §4.1 的完整設計（label、kind／run 身分、每批獨立 issue、冪等）是否有更小的第一步，能先堵住「訊號遺失」而不必一次做完 M3。

### 2　搬頁失敗時，報告不會寫出新網址

| 日期 | 來源 | 舊頁 |
| :--- | :--- | :--- |
| 09-18 | `antigravity/ide-skills` | HTTP 200，meta-refresh → `/docs/skills?tab=ide` |
| 09-24 | `antigravity/rules-workflows` | `.md` 404；HTML 為 meta-refresh → `/docs/rules` |
| 09-29 | `antigravity/changelog` | HTTP 200，meta-refresh → `/docs/changelog` |

**現行行為**：抓取成功、但 token 數低於 `EMPTY_SUSPICION_THRESHOLD`（第 162、590 行）時，只報「抓取成功但一個路徑都沒抽到」。meta-refresh 的目標就在頁面裡（例如 `<meta http-equiv="refresh" content="0;url=/docs/changelog">`），但報告不會寫出來。

歷次決定都是**仍視為失敗、不自動跟隨**，這一點不變。這裡要補的只是診斷訊息：在失敗報告寫出導向目標，讓維護者不必人工去翻。M3-a 另外提到「Markdown 404 的受限替代頁探測」，請評估那是修補現有問題，還是屬於新機制。

### 3　`analyze_report()` 用子字串比對 CI 訊號

**現行行為**：[`monitor_ci_policy.py`](../../../../scripts/monitor_ci_policy.py) 第 27～29 行用 `SIGNAL in report_text`。`check_updates.py` 的 `context_for()`（第 239 行）會把官方原文摘錄原樣放進報告（第 711 行），npm 版本字串也未經驗證就印出。

PR #22 只讓**新增**的診斷與摘要經過 `report_text()` 處理，既有摘錄沒有。實測結果見文末重現指令：原文含 `[SIGNAL: CHECK_FAILED]` 時，`failure` 與 `should_fail` 變成 `True`。

這種注入只會多報（假轉紅、多開 issue），baseline 步驟另有 `git diff --quiet` 保護。根本修法是只認**單獨成行**的訊號，要同時改 `monitor_ci_policy.py` 及相關測試。

### 4　路徑來源與版本 getter 各抓一次

**現行行為**：SOURCES 迴圈（第 579 行）和 `fetch_antigravity_version()`（第 489 行）各自 `fetch(ANTIGRAVITY_CHANGELOG)`。`tests/test_antigravity_changelog.py` 的 `test_equal_version_prints_real_metadata_without_signals_or_write` 斷言 `counts["source"] == 2`，確認一輪會抓兩次。

你在 R7-2 的判斷是：共用正文要改 getter 接線、快取範圍與錯誤重播，會擴大失敗組合。請把這些限制寫成可實作的契約（只在單輪內共用、不跨輪沿用舊正文、抓取失敗時兩者的失敗怎麼呈現）。

### 5　CLI 主版號沒有訊號

`versions.antigravity` 已明確限定為產品版本（PR #22），CLI、SDK、IDE 都不記錄。但本輪三個新 token（`.agents/agents/`、`.agents/skills/`、`~/.gemini/config/plugins`）全部來自 **CLI** 區段，C-55 的複驗節奏也把「CLI 1.x 主版號跨越」列為提前複驗的觸發條件（09-21 計畫 §4.3）。目前這個觸發條件**沒有任何來源能觸發**。

新增欄位要處理 bootstrap、告警門檻與遷移政策。請判斷這算「修補現有機制的缺口」（§4.3 已經依賴這個訊號），還是新機制，並說明理由。

### 6　`.agents/skills.json` 被範本排除

完整證據與五版實測見 [#21](https://github.com/ldsAS/dev-ai-skills/issues/21)。要點：

- agy 1.1.19 內嵌文件要求提交 `.agents/skills.json`；五版範本的 `.agents/*` 會排除它；`.agents/rules.json` 則已放行（C-115）。
- 需要在**現行版本**複驗；`agents.json`、`plugins.json` 的位置**沒有證據**。
- `TOKEN_RE` 抓不到只寫檔名的 `skills.json`，changelog 兩則公告因此沒有觸發任何告警。

### 7　政策列與被取代列干擾比對

`--coverage` 目前是 64 條可偵測／5 條盲區／69 條。盲區中的 **C-117** 路徑欄是範例路徑 `apps/web/.agents/ORIGINAL_REQUEST.md`，屬於防禦政策而非路徑事實，官方文件不可能出現這個路徑，所以它會永遠留在盲區。另外，已被取代的列（例如 C-41、C-42）仍參與比對，被新來源命中時，不代表過去的否定觀察又被證實。

這兩點都在 09-21 計畫 M2 §3.6 的範圍內，請確認 M2 的設計能涵蓋，不需要另開一項。

### 8　CLAIMS 有 7 列不在任何表格內

C-112、C-113（第 50～51 行，前面有空行）和 C-114～C-118（第 172～178 行，前面是引用區塊或空行）都不在「表頭＋分隔線」之後，GitHub 會把它們渲染成純文字段落。`load_claims()` 是逐行比對，監控不受影響。

問題從 C-112 開始，之後每輪都沿用。修法應該很小（移到對應表格內，或補上表頭），但要確認 `CLAIM_ROW_RE` 與 `--coverage` 的結果前後一致。

### 9　C-110 未實機驗證

`~/.gemini/config/skills/` 與 `~/.gemini/antigravity-cli/skills/` 哪一個是 CLI 實際載入的位置，官方文件互相矛盾；安裝器目前寫兩個路徑。需要帶版本號與 active catalog 證據的實機探針。這一項需要實機環境，可能不是你能在本機完成的，請評估可行範圍。
