**觸發**：排程監控於 2026-09-11 06:03 UTC 在 Issue #12 追加留言（[run 34568322059](https://github.com/ldsAS/dev-ai-skills/actions/runs/34568322059)）
**處理者**：Claude Code
**工具版本**：claude-code 2.1.268（報告版）／git 2.55.0.windows.3
**結果**：**訊號本身是文件範例，C-04 未被推翻、五版範本零異動。但循 C-62 的噪音往下查，發現三個結構性缺陷 → 新增 C-100、C-101、C-102；`--coverage` 的盲區由 2 條修正為 7 條。**

> 前一輪（C-97～C-99）修的是「單段 token 往下扇出」和「前導斜線」。
> 這一輪發現那兩條只是同一個根問題的兩個切面 —— **比對規則在三個地方各寫了一份，
> 而且彼此不一致**。本輪把它們收斂成一套。

## 一、這則告警的出處

新增 token：`claude-code/skills` 的 `.claude/commands/frontend/component.md`，標到 C-04、C-62。

逐字位置在 skills 頁「command name source」表格新增的一列：

```
| File in a subdirectory of `.claude/commands/` | Subdirectory path relative to
  `commands/` with each `/` replaced by `:`, then the file name without extension
  | `.claude/commands/frontend/component.md` → `/frontend:component` |
```

它示範的是**命名規則**（子目錄用 `:` 命名空間），不是新的儲存位置。

**機制更早於此**，CHANGELOG **1.0.45** 就有**逐字相同**的例子：

> Custom slash commands: **Restored** namespacing in command names based on subdirectories.
> For example, `.claude/commands/frontend/component.md` is now `/frontend:component`, not `/component`.

原文用 **Restored**，所以機制本身甚至早於 1.0.45。

**範本實測，無需異動**：

| 路徑 | 判定 |
| :--- | :--- |
| `.claude/commands/deploy.md` | TRACKABLE ✅ |
| `.claude/commands/frontend/component.md` | TRACKABLE ✅ |

`!.claude/commands/` 的白名單涵蓋得到巢狀檔案，C-04「團隊共用，應提交」原樣成立。

### 告警的真正成因與 C-04 無關

**該 token 早已存在於 `claude-code/changelog` 的 baseline** —— 正是 CHANGELOG 1.0.45 那一行。
驗證（告警前的 baseline `638f5a8`）：

```
claude-code/changelog -> ['.claude/commands/frontend/component.md']
claude-code/skills    -> []
```

官方只是把同一個例子複製進 skills 頁。比對是**逐來源**進行的，於是一條**已知且已分類**的
路徑被報成新候選 → **C-101**。

## 二、C-62 的噪音：帳本側是同一個問題的鏡像（C-100）

報告同時標了 C-62，但 C-62 主張的是「不要提交 `.claude` 這個路徑本身的 symlink」——
某個 command 檔改名跟它無關。

成因：C-62 的主張路徑是**單段**的 `.claude`，於是**任何** `.claude/**` 多段 token 都會
前綴命中它。全量實測 baseline 156 個 token：

```
命中 C-62 的 token：26 個
  等值命中（真正相關）： .claude 、 .claude/
  往下前綴命中（噪音）： 24 個
    .claude/settings.json   .claude/skills/   .claude/worktrees/
    .claude/commands/frontend/component.md   /.claude/skills/   …
```

**24／26 是噪音。** 前一輪的 C-99 只收斂了 token 單段的方向；這是帳本路徑單段的方向。
→ 前綴比對改為**要求雙方都是多段路徑**，單段的一方只做等值比對。

修正後命中 C-62 的只剩 `.claude`、`.claude/` 兩個；其餘 9 條單段**檔名**主張
（`.geminiignore`、`.mcp.json`、`AGENTS.md`⋯⋯）不受影響 —— 它們本來就不存在「更深的 token」。

## 三、涵蓋率報表一直在高估（C-102）

修好 `claims_for_token()` 之後跑 `--coverage`，數字**完全沒變**。原因是
`report_coverage()` **自己內嵌了一份比對邏輯**，根本沒呼叫 `claims_for_token()`。

也就是說：**涵蓋率報表與告警歸屬長期用著兩套不同規則，而報表那套更寬鬆。**

寬鬆規則會把「不可能見證該路徑變動」的來源算進涵蓋。最清楚的例子：

> `.agents/ORIGINAL_REQUEST.md`（C-55）被算成有 `antigravity/hooks` 涵蓋 ——
> 但那只是因為該來源有一個**裸 `.agents/`** token。
> 上游把這個檔改名時，裸 `.agents/` 不會變，監控不會響。

→ 改為直接呼叫 `claims_for_token()`，兩邊永遠同一套規則。

### 結果：盲區 2 → 7

統一前後全量比對，**24 條主張的涵蓋來源清單改變**，其中 5 條由「有涵蓋」變成盲區：

| 新浮現的盲區 | 原本的取證方式 | 是真缺口嗎 |
| :--- | :--- | :--- |
| **C-83** `.claude/launch.json` | 實地觀察（比對 PM-tools-Dashboard-docker） | **是** —— 受監控的官方頁從未提及此檔 |
| **C-55** `.agents/ORIGINAL_REQUEST.md` | Antigravity 實機實查 | **是** —— 同上 |
| **C-41** `.agents/AGENTS.md` | 實查確認**不存在** | 否 —— 上游無物可比對，盲區在此屬恆真 |
| **C-42** `.agents/settings.json` | 實查確認**不存在** | 否 —— 同上 |
| **C-43** `.agents/settings.local.json` | 規則已移除，仍被 `.agents/*` 涵蓋 | 否 |

**監控並沒有變差，是報表變誠實了。** 這 5 條的依據本來就不是受監控的官方頁，
先前那個「有涵蓋」是假的安心感。

→ 真正的行動項只有一條：**C-83 與 C-55 的複驗不能依賴排程**，要靠時間或明確風險觸發的
人工檢查。已寫進 `README.md` 的〈查監控盲區〉。

> 📌 這件事和 C-90 的教訓同形：當時的結論是「問題不在官方文件，在我們選的來源」。
> 這次是「問題不在監控的偵測能力，在我們報表的算法」。
> **兩次都是自己的工具在騙自己，而不是上游在變。**

## 四、為什麼 C-101 只註記、不抑制

最省事的做法是「token 已存在於其他來源 → 不要報」。**刻意不這樣做。**

「某頁開始或停止提到某路徑」本身仍可能有意義 —— 例如官方正式棄用某個位置時，
它會先從主文件消失、只留在 changelog。直接抑制會把這種訊號一起吃掉。

因此偵測與 baseline 寫回行為**完全不變**，改的只有報告怎麼說：

- 消失項：「**此路徑目前仍出現在** `claude-code/changelog`⋯⋯：它離開的是本頁，不是官方文件整體」
- 新增項：「**此路徑在本次之前已存在於** `claude-code/changelog`：不是全新候選」

新增項查的是 `baseline_sources` 而非當前狀態，所以**兩個來源同時新增**仍會被當成真正的
新候選 —— 這是刻意的，否則同步上線的新機制會被誤判成舊聞。
