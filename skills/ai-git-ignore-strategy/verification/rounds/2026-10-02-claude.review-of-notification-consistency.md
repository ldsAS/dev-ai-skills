## 背景

10-02 的排程（run 36976474189）是 G1 第一次在真實 GitHub 上執行。`gh issue create` 成功建立 #24，但程式建立後立刻、不等待地查了 3 次 issue 列表，碰上 GitHub 列表的短暫延遲而查不到，判定「無法確認是否建立成功」，通知步驟失敗。保護機制正確生效，沒有寫回 baseline。維護者重跑（attempt 2）後找回 #24、寫回 baseline `0dc0af0`。

當時我確認過 #24 的內文沒有走樣：rules 區塊的 hash 等於指紋，逐字比對也通過。所以問題只在「建立後查詢太快」，不在內文。

## 修正內容

| 階段 | 原本 | 修正後 |
| :--- | :--- | :--- |
| 建立後確認 | 立刻連查 3 次列表 | 從 `gh issue create` 的輸出取得 issue 編號，改用 `GET /issues/{n}` 直接讀取並核對 run 標記；只有拿不到可信編號時才查列表 |
| 編輯後確認 | 查一次列表 | 直接 GET 已知編號，必須讀到最新內文才算成功 |
| 每個讀取階段 | 不重試 | 最多 5 次，間隔 1、2、4、8 秒（每階段最多等 15 秒） |
| 不變的部分 | — | create 最多一次；查詢失敗不會被當成「不存在」；身分不符或回應格式錯誤直接失敗，不靠重試掩蓋；workflow、baseline guard、報告格式都沒有改 |

接受的 issue 網址限定為同一個 GitHub 站台、同一個 repo、`/issues/<編號>`，而且只能有一個。網址只是查詢提示，最後仍以直接讀到的內容判定。

## 值得知道的取捨

- **每次開新 issue 前會先多等約 15 秒**：一開始查不到同 run 的 issue 時，會先重試完整個窗口才建立，目的是讓「重跑」有時間看見前一次嘗試開的 issue，避免重複建立。workflow 的逾時是 15 分鐘，影響很小。
- **重試有上限**：GitHub 延遲超過整個窗口時，仍可能確認失敗而轉紅。這時一樣不會寫回 baseline，在那次 run 按 **Re-run all jobs** 就能恢復（10-02 已實際驗證過這條路徑）。

## 合併後

真正的驗收要等**下一次偵測到異動的正式 run**：預期一次就轉綠，log 中不會出現 `Create outcome unconfirmed`，只開一張 issue，並寫回 baseline。

本 PR 不改 baseline，不會和排程推的 bot commit 衝突。
