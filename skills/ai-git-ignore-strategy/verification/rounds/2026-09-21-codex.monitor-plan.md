## 2. 第一階段：恢復來源並建立無副作用的驗證方式

### 2.1 來源清單

涉及 `scripts/check_updates.py` 的 SOURCES、來源 fixture 及 `scripts/last_checked.json`。

1. Antigravity `skills` 改用已驗證的 `https://antigravity.google/docs/skills.md`，其內容包含 Antigravity 2.0、CLI、IDE 三種 surface。移除已被併入的 `ide-skills` 來源與其退休 baseline key，記錄舊新對照。
2. 逐一確認 `hooks`、`rules-workflows`、`plugins`、`subagents`、`gcli-migration` 的 `.md` 端點。只有 HTTP 成功、取得實際文件且完整保留對應 surface 的才切換；不假設每個 HTML 頁都有可用 Markdown。`changelog` 不套用這個推論。
3. 不增加通用 meta-refresh 跟隨器：本次已知來源搬遷可由精確 URL 修正，避免擴大抓取行為。保留空集合警戒、重試與失敗保留 baseline 的現行語意。
4. Claude 的既有三個 docs.claude.com 來源改用對應 `code.claude.com/docs/en/*.md`，維持 source key。補列 `hooks.md`、`desktop.md`、`claude-directory.md` 前，先完成人工 token 分類；新增來源的 bootstrap 不等於內容已審查。
5. C-105 必須逐一確認兩個記憶目錄的具體 token 與正式來源，不以主張整列「只命中其中一個路徑」代替兩個路徑的驗收；`.claude/` 這種父目錄不能算通過。來源未接入前保留帳本的盲區註記。

### 2.2 baseline 遷移

1. 固定最新 main SHA、source URL、抓取時間與內容摘要；在 PR 附上逐來源 added / removed / preserved token 表。
2. 只更新明確遷移或新增來源的 key，退休 `antigravity/ide-skills`；不整包重抓覆蓋其餘來源。先把真實新機制登記入帳，再接受新版文字的 baseline。
3. 不藉此抑制既有未解問題。CLI 全域路徑仍是 C-110「有疑」，移入新 baseline 不會讓它自動結案。
4. 合併前若 bot 又更新 main，重新比較來源與 baseline 的最新差異，不以舊快照覆蓋 bot 新資料。

### 2.3 E2E 的副作用隔離

現有 `workflow_dispatch` 在分支上仍可能留言、關閉 failure issue、commit / push baseline；「分支測試」本身不是安全邊界。

- 增加明確的 dry-run 輸入，手動執行預設 dry-run；排程保留正式模式。
- dry-run 用 `check_updates.py --dry-run`，禁止通知、恢復關閉與 baseline commit 步驟，保留報告及失敗狀態供審查。測試驗證三個外部寫入步驟確實跳過。
- 本機先跑 fixture / live dry-run，再於獲准的遠端驗證範圍內執行。修正部署後正式排程成功才可自動恢復 #16；不得預先手動關閉來掩蓋紅燈。

## 3. 第二階段：告警歸屬與覆蓋率

1. 以 M0 審查並整合後的 C-100～C-102 為基礎處理後續歸屬問題；範本修正與已查證事實的登記本身不必等 PR 合併，但未覆蓋的來源必須明確標記為盲區。
2. 保留 token 集合變動偵測；跨來源註記只補充背景，不能無條件消音。
3. 修正「單段目錄」一詞：檔名與目錄型 token 分開描述。父目錄消失但仍有子路徑的情境，顯示支持它的來源，不宣稱所有子主張失效。
4. 明確處理帳本 glob，例如 C-76 `.github/hooks/*.json`；限制規則在已定義的路徑語法內，補正／反例，避免寬鬆匹配所有後代。
5. 明確區分「有 token 可對應」與「支持該工具的語意主張」。例如 Claude 新增 `AGENTS.md` 不會推翻 Antigravity 的 C-50；建議加入工具 scope 與來源證據的可解析欄位，先定義 schema 與遷移表，再實作，不能靠 AI 摘要判定。
6. 反向主張及被取代主張要有明確狀態：已移出或被取代列不應當成活躍正向涵蓋率；「官方不讀此檔」不能因缺 token 就列為失效。仍保留歷史列與取代關係，不刪證據。
   - 統一分類狀態值與 `被取代→C-XX` 的取代關係，再供載入、歸屬與涵蓋率共同使用，不在各函式各寫一套規則。
   - 固定回歸案例：`~/.gemini/config/skills` 不再命中 C-47，但保留 C-110、C-111；`~/.gemini/antigravity/skills` 不再命中 C-48，但保留 C-111。歷史列仍存在帳本。
   - 狀態「有疑」仍是待驗主張，不能跟「被取代」一起被排除。反向主張另定語意欄位，不能靠散文中有「不」字推論。

## 4. 第三階段：通知與既存 token 的稽核

### 4.1 通知

- 用專用 label 加機器可讀的 kind / run 身分辨識，標題只負責呈現。
- 異動每批建立獨立 issue，同一 run 的重試須冪等，避免新訊號埋進舊 issue。
- 來源故障沿用一張帶穩定標記的 failure issue；相同失敗指紋不每天追加同文，有新原因、受影響來源改變或恢復才更新。
- 異動與失敗同時發生時，各自只放相關段落，互相連結，不貼兩份全文。AI 摘要維持非判斷來源。
- #15、#16 以明確 issue 編號建立一次性的遷移處置，不再只靠相同標題尋找，也不關閉其他人工 issue。

### 4.2 全量分類稽核

- 新增唯讀 audit 模式，列出所有現有 baseline token 的工具／來源、對應主張、分類及既有範本案例；補查初始化時已存在而從未變動的 token。
- 報表分清家目錄、專案正式機制、否定敘述、範例與未知，不自動由 token 推導 ignore 規則。
- 有主張但缺案例、只有寬前綴命中、未分類 token 均列為待審，不與每日路徑變動告警混為同一語意。
- 尚無 token 的語意變化仍是盲區。C-55 的實機／binary 複驗採以下節奏，不暗示文字監控能取代它，也不宣稱 C-55 是唯一涉及隱私的主張。

### 4.3 C-55 的人工複驗節奏（計畫，未建立排程）

- M3 首輪先補一次現行版本複驗，作為後續日期基準；其後每三個月一次。
- Antigravity 產品 2.x 或 CLI 1.x 任一主版號跨越，或已觀察到工作區產物／prompt 儲存機制變更時，提前複驗並重設三個月週期。紀錄同時寫明產品與 CLI 版本，不能混用兩者版號。
- 在隔離測試工作區用無敏感資料的固定 probe，核對 `.agents/ORIGINAL_REQUEST.md`、子目錄變體、逐字內容與時間戳行為，以及範本是否攔截。binary 路徑字串只作輔證，不代替實際寫入觀察。
- 無法做實機時明寫未驗證及剩餘風險；僅靜態字串命中不算重設「實機已驗證」日期。新版移除舊位置時先查是否改寫到其他位置，不直接放寬 ignore。
- 執行結果追加至 rounds，引用回 C-55；結果變更時依帳本規則新增主張並保留舊列。實驗與自動排程另依執行時的授權範圍安排，本文件不建立自動化。
