## 二、做得好的地方

- **來源與版本一起修**，不先只換 URL 讓來源轉綠、版本卻繼續靜默回傳 `None`。
- **`versions.antigravity` 明確限定為產品版本**，CLI／SDK／IDE 不混進來。IDE 區段也用 `/releases?tab=` 連結，而且也是 2.x，不限定區段遲早會誤判。
- **拿掉會猜測其他產品版本的舊格式 fallback**，也不自動跟隨 meta-refresh。
- **解析失敗走既有的 `CHECK_FAILED` 分支**，不全域改 npm getter 的 `None` 語意，範圍控制得很好。
- 測試表明寫「不得用固定回傳的 stub 冒充版本解析驗證」，並沿用 PR #19「讓另一個來源變動、強制寫檔、比對整份 payload」的設計。
- 三個 token 的分類都**保留證據邊界**：`.agents/agents/` 不因公告升級成欄位或團隊分享定位的證據，plugins 公告不拿來替代 C-110 的 skills discovery 驗證。
- hash 的計算方式（解碼後重新編碼 UTF-8、不是傳輸位元組）有寫清楚，我因此能逐位元重現。

## 三、實作前建議修正

### R1　「可辨識為發行記錄」要定義，而且要比合格文法寬

計畫 2.2 第 5 點說，可辨識為發行標題／release link 的記錄，格式錯了就要報錯，不能跳過後回退到舊版本。但第 2 點用「`### [vX.Y.Z](...)` 加上合格連結」來**辨認**發行記錄。

辨認條件和合格條件如果是同一組，「格式錯誤」根本進不了報錯分支：

```markdown
## Antigravity 2.0

### v2.19.0

Latest

October 5, 2026

### [v2.18.1](/releases?tab=hub&version=2.18.1 "View release 2.18.1")
```

`### v2.19.0` 沒有連結，照第 2 點不算發行記錄，照第 5 點又被當成一般功能標題。結果 parser 回傳 2.18.1、不報錯 —— 正是第 5 點要防的「跳過損壞的新記錄後回退舊版本」。

建議把兩層分開：

| 層次 | 條件 | 不符時 |
| :--- | :--- | :--- |
| 辨認（寬） | H3 以 `[v` 或 `v<數字>` 開頭，或含 `/releases` 連結 | 視為一般功能標題 |
| 合格（嚴） | 計畫第 2、3 點的完整文法 | **報錯** |

目前產品區段裡的功能標題沒有一個會被寬條件誤認（SDK 那兩個帶版本字串的標題也不是以 `v` 開頭）。失敗測試請加上「最上方是無連結的新版標題」與「連結 `tab` 或 `version` 不一致」兩例。

### R2　刪掉 prerelease 的處理

第 4 點「合法 prerelease 不列為穩定版候選」、第 6 點「只有 prerelease 時拋出例外」都假設有一種已知的 prerelease 寫法。但四個區段 132 個發行標題裡**一個都沒有**，所以「合法」的格式只能用猜的。

而且「略過」本身就是靜默路徑：若官方哪天在最上方放 `### [v2.19.0-rc.1](...)`，parser 會回傳 2.18.1、不報錯。這和計畫第 51 行自己的原則（「先產生可見失敗，再依新證據更新對應」）衝突。

建議：**任何能辨認為發行標題、但版本不是 `X.Y.Z` 的記錄一律報錯**。真的出現 prerelease 時，再依當時的實際格式決定要不要排除。這也讓第 6 點少掉一個分支。

### R3　區段隔離需要人為製造的反例

真實資料中，**全文所有發行標題的最大版本恰好就是 2.18.1**：IDE 2.5.5、CLI 1.2.11、SDK 0.1.18 都比較小。所以：

- fixture 若只保留「真實發行標題結構」，就算 parser 完全不限定區段、直接取全文最大值，「正常解析」這組測試照樣全過；
- 計畫第 100 行的兩個反證（只換 URL、改回 `None`）都測不到區段隔離。

建議：

1. fixture 在非產品區段放一個**比產品版本大**的合格發行標題（例如 IDE `### [v2.99.0](/releases?tab=ide&version=2.99.0 ...)`），並在 fixture 註明這是刻意加的；
2. 加第三個反證：**拿掉區段限制、改取全文最大值時，測試必須轉紅**。

計畫測試表的「其他區段更大版本不影響結果」有寫到這個意圖，但沒寫出真實資料不具備這個條件，實作時很容易只用真實片段就交差。

### R4　驗收要求的證據，正式 run 的報告裡不會出現

`main()` 只在版本**有變**時才寫進報告（`version_notes` 或 `version_alerts`）。計畫 4.3 會先把 `versions.antigravity` 遷移成 2.18.1，所以上線後第一次正式 run 解析出 2.18.1 時，報告只會顯示「✅ 無異動」，**完全不提 Antigravity 版本**。

計畫第 117 行要求的「版本結果非空且屬產品區段」只能這樣推論：parser 失敗會拋例外 → 沒有 `CHECK_FAILED` → 應該有解析到。但這個推論本身依賴程式接線正確，而接線正確正是驗收要確認的事。第 17 行提醒過「exit 0 不等於監控健康」，這裡是同一類情況。

建議二選一（我傾向第一種）：

1. 報告固定印一行本輪取得的版本與出處，例如在報告末尾的 `<details>` 裡列 `antigravity: 2.18.1（## Antigravity 2.0 區段）`。這不改訊號格式，也順帶讓 npm getter 回傳 `None` 時看得出來；
2. 不預先遷移版本，讓第一次 run 以版本參考項顯示 `2.17.0 → 2.18.1`。缺點是只有第一次看得到。

## 四、建議登記為後續項

### R5　`.agents/skills.json` 是官方建議提交的團隊檔，範本會擋掉

計畫第 3 節對 `.agents/skills/` 寫「公告只列檔名的部分不自行補成完整路徑」。只看 changelog，這個證據紀律是對的，但有兩則公告值得往下追：

- **產品 v2.11.0**（Markdown 第 345 行）：新增從專案子目錄的 `skills.json`、`agents.json`、`rules.json` 探索自訂 skills／agents／rules；
- **CLI v1.2.10**（第 908 行）：`skills.json`、`rules.json`、`agents.json`、`plugins.json` 的目錄登記改為只載入直接子項。

我在本機 `%LOCALAPPDATA%\agy\bin\agy.exe`（`agy --version` 為 **1.1.19**）內嵌的文件找到位置與用途：

> Create and commit a `skills.json` at the root of your repository (in `.agents/skills.json`)

同一段接著說明：隊友 clone repo 後，agent 會自動找到 `.agents/skills.json` 並載入共用 skills。

但範本在 [`generic/SKILL.md` 第 429 行](../../generic/SKILL.md) 用 `.agents/*` 排除整個目錄，只另外放行 `rules.json`（C-115）。**照官方建議做的團隊，`.agents/skills.json` 會被靜默忽略**，情況與 PR #19 修掉的 `.agents/rules.json` 一樣。

監控也看不到這件事：`TOKEN_RE` 只抓帶路徑前綴的 `.agents/...`，而 changelog 只寫單獨的檔名。

建議**不併入本批**（本批的目標是讓 #20 盡快轉綠，改範本要另做五版的 Git 邊界驗證）。維護者已將這一項登記為 [Issue #21](https://github.com/ldsAS/dev-ai-skills/issues/21)，裡面附有五版範本的實測結果；計畫第 7 節引用 #21 即可。後續處理要注意：

- 證據：上面兩則公告與 agy 1.1.19 的內嵌文件。**版本早於 CLI 1.2.10，要在現行版本複驗**；
- `agents.json`、`plugins.json` 的位置**我沒找到證據**（二進位裡只有單獨的檔名），不要類推；
- 同一段內嵌文件寫明 `path` 可以是絕對路徑或 `~/` 路徑。放行時要比照 `rules.json` 在 C-115 的寫法加上提醒：核對實際解析位置、避免暴露個人目錄。

### R6　產品升 3.0 時，major 告警很可能變成「找不到產品區段」

區段名稱 `## Antigravity 2.0` 本身帶著主版號。產品若升到 3.0，區段很可能改名為 `## Antigravity 3.0`，parser 會以「缺少產品區段」失敗。原本該出現的「⬆️ 版本跳動」告警會變成 `CHECK_FAILED`。

這仍然看得到，符合計畫的失敗優先原則，**我同意不放寬比對**。但建議錯誤訊息列出**實際看到的所有 `##` 標題**，並提示「可能是主版號改名」，讓失敗報告本身就能說明原因，不必另外人工翻頁。這與 M3-a 的搬頁診斷是同一個方向。

## 五、R7　次要項目

1. **版本 label 要一起改**：[`check_updates.py` 第 496 行](../../../../scripts/check_updates.py) 的 label 仍是 `antigravity.google/changelog`，會出現在 `version/<label>` 失敗診斷與 major 告警的「來源」欄，不改就會指向已失效的網址。
2. **同一份 268KB 的文件每輪抓兩次**（SOURCES 迴圈一次、版本 getter 一次）。兩份快照可能不同（官方說會逐步推出），暫時性失敗的機率也加倍。共用同一份內容可以讓 2.3 的部分失敗組合少一種（「來源抓取失敗但版本抓取成功」）。選做。
3. **合併前要再對最新 main 做一次深度比對**。計畫只寫「實作前取得最新 main」，但 bot 在實作與 review 期間仍可能推 baseline（本機落後的兩個 commit 就是這樣來的）。若 `versions` 區塊相鄰的行被 bot 更新，合併時會衝突。
4. **CLI 的主版號跳動目前完全沒有訊號**。本批三個新 token 全部來自 CLI 區段，CLI 才是這個 skill 路徑事實的主要來源。同意不在本批加欄位（新 key 需要 bootstrap），但可以列進 M2／M3 的清單。
5. **fenced code 的處理**：目前文件裡沒有任何 fence，保留這條防護無妨，但**未閉合的 fence 應該報錯**。否則它會把後面的 `##` 標題全部吞掉，區段邊界就悄悄消失了。
