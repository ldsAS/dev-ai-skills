## 2. 修正契約

修改 `scripts/monitor_notifications.py`：

1. 初始 run 身分查找仍掃描全部 open／closed 分頁；沒找到或 gh 查詢失敗時，有限次退避再讀。查詢失敗不能當空清單授權 create；多重身分、錯 repository 或 malformed 回應仍失敗。
2. **create 最多呼叫一次。** 從 stdout 的完整 issue URL 取編號，只接受目前 GITHUB_SERVER_URL（預設 github.com）、同一 repository、`/issues/<正整數>`，且只出現一個候選。不接受外站、其他 repo、PR 或多個 URL 所指的編號。URL 只是查詢提示，不能當作成功證據。
3. 有可信編號就用 `GET /repos/{repo}/issues/{n}`；核對回應的 repository_url、number、state、非 PR 以及精確 run marker，再沿用實際 rules 正文與 SHA 的交付判定。即使 gh create 非零，若已取得合法 URL，仍可讀回確認；不因 exit code 或 URL 單獨宣告成功。
4. create 沒有可用 URL（包含成功但丟回應）時，才以同一 run 身分的列表查詢恢復。超過預算仍未確認就失敗，**不再次 create**。
5. 編輯只執行一次，之後直接 GET 已知 issue 編號，讀到舊正文、缺 marker 或暫時 API 失敗時退避。必須讀到同編號、open、marker 正確、SHA 及實際正文相同才成功；看見 closed 立即交回原本的失敗判定，不重開。原先「已 closed 且同一報告可視為已交付」的重跑政策保留。

每個讀取階段最多 **5 輪**，失敗／未就緒時依序等 **1、2、4、8 秒**，額外等待上限 **15 秒／階段**。最多三個階段（初始列表、create 確認、必要的 edit 確認），至多 45 秒刻意等待；**不含 gh 網路時間與各輪完整分頁的 API 請求時間**，不宣稱整個命令 45 秒硬 timeout。全新 run 的初始空列表也會經過 15 秒確認窗口，降低重跑時尚不可見就重建的機會。讀到正確結果便立即停止；已知身分不合法不靠重試掩蓋。

未改 workflow、baseline guard、報告格式、issue 身分、baseline schema 或 checker。沒有新增偵測機制。
