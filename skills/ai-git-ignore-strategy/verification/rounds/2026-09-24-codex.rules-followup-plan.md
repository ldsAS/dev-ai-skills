### 7.4 遠端及 issue 收尾

後續發布階段以最終 commit 的 template／monitor CI 通過為準；如執行 GitHub dry-run，確認通知、恢復結案、baseline commit 三項寫入步驟均 skipped。dry-run 的成功不能證明正式恢復步驟已執行。

分開記錄兩種完成狀態：

1. **修復交付完成**：有限 diff、帳本、五版範本、測試、隔離安裝及最終 commit 的 CI 都可核對。
2. **正式告警恢復完成**：修復合併後，一次正式排程在全部當時配置來源成功的前提下，確實執行恢復步驟並處理 #16。尚未觀察到就記「待正式排程驗證」，不手動關閉 #16 代替，不為等待此項自行新增 automation。

#15 的新訊號逐項分類與修復結果記在本輪紀錄；不因 baseline 已吸收或本批修復成功，就把仍屬 M2 的事項一併宣告完成。本次定稿不觸發遠端 workflow 或發送留言。

## 8. 交付順序與後續邊界

1. **本批 P1～P3 作為一個一致的修復批次**：先校正最新基底與來源證據，再同步來源／有限 baseline、五版範本及帳本，最後跑上述驗收。可拆成可審查 commit，但不得先發布只吸收新路徑、尚未分類／修正範本的 baseline。
2. **M2 另案**：處理跨工具 scope、glob、單段檔名分類、歷史／待驗／負向主張與涵蓋率語意。納入 C-24／C-78 等正向位置盲區；先定輸出與測試再動算法。
3. **M3 另案**：處理新訊號追加至即將結案 issue、baseline 已吸收後不再提醒、去重與恢復身分。理由是告警生命週期風險，不是「每天都有留言」。與 M2 可分開交付，但不搶在本批已確認缺口之前。
4. **M3-a：來源搬頁診斷**，排在本批後的下一個獨立小項。對取得的 meta-refresh 正文顯示解析出的轉向目標，仍視為失敗、不自動跟隨；Markdown 404 的替代 HTML 探測須另定範圍及測試。本批不實作 parser、探測或 issue 機制。

若驗收發現阻擋，精準撤回有問題的本批規則／程式變更並保存失敗證據；baseline 必須與最新 main 逐項合併，不整份退回舊版蓋掉 bot 更新，也不移除失敗來源隱藏問題。單一實作者整理此批變更，Claude 可在完成後獨立 review；本文件不自動派工或授權另一方同時改寫相同檔案。
