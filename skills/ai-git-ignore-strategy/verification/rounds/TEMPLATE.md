# 交接包模板

複製本檔為 `YYYY-MM-DD-<tool>.md` 後填寫。收到包的工具**沒有本專案的任何上下文**，
所以每一份包都必須自帶背景、指令與期望格式。

---

## 撰寫規則

1. **每題都要三件事**：目前 skill 怎麼寫、官方文件怎麼說（含摘錄與取證日）、要跑什麼指令。
   只問「這個檔案存在嗎」，對方無從判斷你要的是哪一版行為。
2. **必問版本號與 OS**。缺版本號的回覆一律視為 `未驗證`（見 [`../README.md`](../README.md)）。
3. **要求區分「我實際看到」與「我推測」**。AI 自我回報容易把訓練知識當成觀察結果，
   C-41／C-42 就是這樣落到 `有疑` 狀態的。
4. 回填區用固定格式，方便逐條更新回 `CLAIMS.md`。

---

# 【交接查核】<工具名> 路徑確認 — YYYY-MM-DD

## 這是什麼

我維護一個開源專案 [`dev-ai-skills`](https://github.com/ldsAS/dev-ai-skills)，
其中的 `ai-git-ignore-strategy` skill 會告訴 AI 助理：哪些 AI 工具產生的檔案該進 Git、哪些該擋。

這個 skill 的正確性取決於一組**路徑事實**。我已經用自動化機制比對過各工具的官方文件，
但有幾項**在官方文件中查無依據，或文件與實際行為可能有落差**，需要在實際裝有 <工具名> 的環境確認。

**請以你實際看到的檔案系統狀態回答，不要依據訓練知識推測。**
若某項無法確認，直接寫「無法確認」比猜測有用。

## 先回報環境

```text
工具名稱與版本：
作業系統：
測試用專案路徑：
```

> 版本號是必填。沒有版本號的話，這份回覆日後無法與官方文件的時間軸對照。

## 請先執行

```bash
<列出實際指令>
```

## 待確認項目

### Q1. <一句話問題>

- **目前 skill 怎麼寫**：<現行規則或敘述>
- **官方文件怎麼說**：<摘錄；若查無依據就寫「查無依據」>
- **請確認**：<具體要看什麼>

（重複 Q2、Q3⋯⋯）

## 回填格式

請照下列格式回覆，一題一段：

```text
### Q1
存在：是 / 否 / 無法確認
實際路徑：
用途（你觀察到的）：
應提交或應排除：提交 / 排除 / 需視情況
依據：我實際執行了什麼、看到什麼
信心：高 / 中 / 低
```

最後補一段自由敘述：**有沒有我沒問到、但你認為這個 skill 該涵蓋的路徑？**
